# 阶段开发日志规范

每个 Phase 只保留一份开发日志，不为普通增量新建日志文件。文件名固定为：

```text
YYYYMMDD-Phase-X-开发日志.md
```

每次准备提交 Git commit 前，在当前 Phase 文件最上方追加一轮，最新在上。内部标题固定为：

```text
YYYY-MM-DD HH:mm · Phase X · 第 N 轮 · 本轮任务
```

每次日志更新使用以下结构：

1. 本轮任务列表
2. 用户 Assignment 与导师引导
3. 本轮任务完成度
4. 测试方式
5. 测试结果
6. 用户如何进行手工测试
7. 风险预估与规避
8. 下轮建议
9. 本轮任务大白话讲解
10. 面试官可能追问的技术细节以及如何回答

记录原则：

- 写真实完成内容、实际命令和退出结果；未运行就明确写未运行。
- 只记录关键限制与用户疑问，不复制完整 diff、终端输出或整段 Agent 对话。
- 大白话部分先讲业务目的、用户看到什么和数据流，再讲专业术语。
- 历史错误和修正都保留结论，不能把失败改写成一次成功。
- Commit SHA 可在提交后下一轮补记；Git 历史是原始旧日志的长期追溯入口。
- “本轮任务完成度”附带大致耗时、Token（宿主可见时）、子 Agent 数，以及业务代码/测试/文档的改动量；未知就写“不可见”，不得编造。
- “测试方式/结果”列出实际测试命令和运行次数；同一命令因修正重跑时记录总次数，不复制完整终端输出。
- 连续 30 分钟没有业务代码、可运行测试、已确认决定或明确阻塞证据时，在“风险预估与规避”记录停止原因和缩小范围结果。
- 每个阶段步骤第一次进入日志时，必须给出 Assignment：业务背景、必要性、代码入口、输入/输出、完成标准、建议 test case、不应修改的边界、提示梯度、预期耗时和 2–3 个面试追问；记录用户是否尝试、遇到什么阻塞、Agent 在哪一步接手以及原因。
- 用户对话默认不写入日志。只有用户明确要求记录问题、疑惑、阻塞或反馈时，才逐字保留相关原文，并紧随证据、导师解释、结论和复习动作。
- 阶段出口日志必须追加 Rubric 9 维度分数、likelihood/impact 风险登记、P0–P3 处置、独立对抗审查轮次/原始结论/最终 `PASS`，以及至少 5 个基于真实工作的问答练习。用户未作答的题目标记 `待练习`。
