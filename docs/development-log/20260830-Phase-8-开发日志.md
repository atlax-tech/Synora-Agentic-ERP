### 7. 风险预估与规避

- P1：跨用户/公司召回风险。本轮用不可变 `MemoryScope` 全字段精确相等比较，缺失的 warehouse/run 不会扩大范围；后续仍需 Frappe 服务端权限矩阵和猜 ID 测试。
- P1：候选或旧版本冒充事实风险。只有 `APPROVED` 且未到期的非 Working 记录可召回；纠正要求新 identity 和递增 version，旧记录不被原地覆盖。
- P1：记忆内容注入能力风险。内容固定为 `UNTRUSTED`，严格模型禁止 `allowed_tools`、权限或策略字段；后续必须在完整 ContextBuilder→Provider 链复验。
- P2：`CANDIDATE` 与产品持久状态 `PENDING` 的命名差异。本契约暂时兼容两种候选拼写，后续 Frappe 存储需统一规范化为批准方案中的 `PENDING`，不得把任一候选状态当作可见事实。
- 未选择任何数值 TTL；Episodic 仅在批准状态要求显式 expiry，避免编造保留期。

### 10. 面试官可能追问的技术细节以及如何回答

- 问：为什么 scope 要求所有字段精确相等？答：可选字段代表更窄边界，省略不能被解释成“全部可见”，否则会产生跨仓库或跨 Run 的隐式扩大。
- 问：为什么候选不能直接召回？答：候选正文来源不等于业务事实，必须先经过对应权限主体审核；召回门只接受 `APPROVED`、未过期且精确范围匹配的记录。
- 问：为什么纠正要新建版本？答：原记录需要保留审计和可追溯关系；新内容先是候选，旧内容停止召回，不能用原地编辑掩盖历史。
- 问：为什么不在这里设统一 TTL？答：产品只要求审核时的 Episodic 到期和来源版本约束，没有批准统一数值；擅自设 TTL 会把未经证实的策略写进安全边界。以上问题均为待练习。
