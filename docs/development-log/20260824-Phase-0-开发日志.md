### 用户如何进行手工测试

### 本轮任务大白话讲解
这轮是在规定“以后怎么开发、什么能做、什么绝对不能绕过”，避免 Agent 为了快而直接改 ERP 数据或伪造测试结果。

### 面试官可能追问的技术细节以及如何回答
- 问：为什么需要 Harness？答：让需求、架构、测试和证据在仓库里可追溯，但 Harness 不能代替业务测试。
- 问：为什么后来精简？答：治理收益必须覆盖成本；普通增量采用风险分级，安全关键和阶段出口才升级审查。

### 本轮任务列表
- 建立 `ARCHITECTURE.md` 和 `DESIGN.md`。
- 确认 ERPNext 为事务事实源，Runtime 不直连数据库，RAG/Multi-Agent 按证据演进。

### 本轮任务完成度
已完成并提交：`8140c78`、前端设计纠偏相关提交。

### 测试方式
交叉检查 PRD、架构、设计和安全边界是否冲突。

### 测试结果
未发现权威冲突；未决技术均保留为未决，没有提前声称采用。

### 用户如何进行手工测试
从 PRD 的一项需求追到架构边界和设计义务，确认没有被阶段拆分删除。

### 风险预估与规避
目标架构可能被误当成已实现架构；文档用事实状态区分当前与未来。

### 下轮建议
建立测试、验收和工程规格，使后续实现可机械验证。

### 本轮任务大白话讲解
这轮决定系统各部分怎么分工：ERP 管业务事实，Synora 管 Agent、权限和受控操作，模型不能自己算钱或直接写单据。

### 面试官可能追问的技术细节以及如何回答
- 问：为什么 Runtime 与 Frappe 分开？答：隔离模型运行环境与 ERP 权限面，所有 ERP 操作只能走受控 Gateway。
- 问：为什么不立刻上向量库和多 Agent？答：先有单 Agent/FTS5 基线，只有实测净收益才增加复杂度。

## 2026-08-24 12:59 · Phase 0 · 第 4 轮 · 建立 PRD、审批基线与工程规格

### 本轮任务列表
- 合并产品需求到 `docs/PRD.md`，补齐完整 P2P 范围。
- 确认 Draft 与 Submit 分离、显式确认、职责分离等审批原则。
- 建立 SPEC、TESTING、ACCEPTANCE 和 ROADMAP。

### 本轮任务完成度
已完成并提交：`fb14bdc`、`bbb7538`、`1da487f` 及相关工程规格提交。

### 测试方式
检查 F-001–F-015 是否都有阶段和验收出口；检查未决项是否明确路由。

### 测试结果
需求范围保持完整，未为实现方便删除高风险写入、审批、回执和对账要求。

### 用户如何进行手工测试
在 PRD 中选择一个功能编号，对照 SPEC 和 ROADMAP 查到实现阶段及验收结果。

### 风险预估与规避
文档量增加可能降低理解效率；当前规则要求按业务链路按需阅读，不再默认通读全部文档。

### 下轮建议
让执行计划只负责排序，不重新解释产品事实。

### 本轮任务大白话讲解
这轮把“产品最后要做到什么”说全：先读数据，再给建议，再审批写入，最后覆盖完整采购生命周期。

### 面试官可能追问的技术细节以及如何回答
- 问：为什么先定审批再写代码？答：企业写操作的身份、职责分离和失败恢复会决定数据模型与接口，不能事后补。
- 问：如何避免阶段拆分缩水？答：需求始终留在 PRD，ROADMAP 只安排交付顺序。
