- 为什么未知结果要改变 Run 状态而不是只标 Receipt？回答：Receipt 描述副作用，Run 是调度闸门；只有同时冻结 Run，恢复器才不会在结果不确定时继续生成下游 Action。
- 为什么历史草稿回读允许 docstatus 变化？回答：草稿 Receipt 本身已经是过去发生的创建事实，后续 Submit/Cancel 是另一份独立批准事实；允许有限状态推进只为显示历史，不能让当前 Submit/Cancel 通过错误状态。
- 为什么真实验收不在 teardown 取消单据？回答：阶段方案要求记录测试产生的单据并保留失败证据；取消会改变父单累计状态，导致历史 Receipt 不能重读，也会把“真实成功”变成不可复核的假清理。
- 浏览器截图能证明什么？回答：它证明真实登录态下 Runs 页面展示服务端保存的成功/对账状态和脱敏回执；业务正确性仍以 Frappe 测试与数据库回读为准，截图不替代权限和并发测试。

### 10. 面试官可能追问的技术细节以及如何回答

- 为什么不能把取消做成数据库回滚？回答：ERPNext 取消会生成库存和 GL 逆向事实，并更新下游累计状态；数据库回滚无法替代业务冲销，也会破坏审计，所以每个取消是独立 action、独立审批和独立 Receipt。
- 为什么 PI 取消前必须先取消 Payment Entry？回答：固定上游的 Payment Entry 引用会使发票仍有活动付款链接，PI controller 会阻止取消；即使 controller 没有阻止，也必须先恢复 outstanding，再取消发票。
- 如何确认 PR 取消真的恢复库存？回答：不只看 PR docstatus，而是读取该 PR 的全部 Stock Ledger Entry，要求原始与反向数量净额为 0，同时核对 PO Item received_qty 与剩余已提交收货合计。
- 响应丢失时为什么不能重新调用 cancel？回答：取消是不可重复的业务副作用；先用目标状态、库存/GL 和发票余额判断是否已发生，未知时进入对账或人工介入，避免把恢复动作变成第二次业务写入。
- 父单累计进度为什么允许回放时变化？回答：合法后续取消会改变 PO/PR 的 received/billed 汇总；Receipt 固定目标、链接、状态和账务证据，只对明确的累计进度字段做受限历史快照匹配。

- 为什么不能根据“Payment Entry 单据存在”就说付款成功？回答：草稿存在没有 GL 副作用，提交成功也可能在响应返回前断连；必须读回 Submitted 状态、引用分配、发票 outstanding/status 和平衡 GL。
- 为什么创建草稿也要独立审批？回答：草稿会锁定一个付款引用并可能被后续提交，创建与提交分别绑定 digest、幂等键和回执，任何一步都不能替另一动作授权。
- 如何避免两个付款同时超过发票余额？回答：审批后执行前重新读取余额，发票父单上的连接级命名锁把两个草稿转换串行化，锁内再检查未结草稿和 ERP 当前余额；输掉的动作返回冲突，不重试 controller。
- 为什么只支持同币种付款？回答：当前 typed payload 没有可信汇率输入，ERPNext 汇率/科目配置由 controller 决定；发现账户币种和发票币种不一致就 fail closed，避免模型猜税额或汇率。
- 付款提交失败时如何恢复？回答：保留真实 Draft 和失败 Receipt，Run/Action 进入可审查失败状态；确认没有提交副作用后才能重新提出新的提交动作，未知结果必须先做只读对账。

### 10. 面试官可能追问的技术细节以及如何回答

- 为什么 PR 草稿必须通过 PO mapper？回答：mapper 保留 ERPNext 的来源行、价格、仓库和必填默认值；Agent 只覆盖审批过的数量，不自己重建业务单据。

- 部分收货如何避免不同来源行串行？回答：payload 必须携带唯一来源子表行，mapper 和 Receipt 都核对 `purchase_order_item` 与父 PO，来源行不一致直接冲突。
- 如果提交响应丢失怎么办？回答：reservation 保留动作身份，后续只读对账依据目标单据和关键字段分类成功或人工接管，不能盲目重新提交。

### 10. 面试官可能追问的技术细节以及如何回答

- 为什么 Run 没有在一个 PO Submit 完成后关闭？回答：Phase 10 是跨单据长任务，单 Action 完成不代表收货、开票和付款都完成；Run 终态要等后续 PlanStep 的事实确认。
