### 9. 本轮任务大白话讲解

这一步把“提交采购订单”变成一条可追责的业务动作：Buyer 只能提出，Approver 必须在自己的权限和公司/仓库范围内批准，Approver 执行时服务器再次检查 PO 仍是草稿，ERP controller 完成 Submit，随后系统读回 `docstatus=1` 才写成功 Receipt。用户在 Runs 页面能看到独立审批队列；批准后同一个审批人仍能看到执行按钮，提交成功后重复点击只回放同一份结果，不会再提交第二次。

### 10. 面试官可能追问的技术细节以及如何回答

- 为什么批准后还要再次检查权限和范围？回答：批准是带有效期的事实，执行前公司、仓库、DocPerm 和来源状态都可能变化，服务器必须以当前 ERP 事实重新决定是否允许写入。
- 租约过期后为什么不能直接重试 Submit？回答：进程可能已经在 ERP 完成 Submit，重试会产生重复副作用；先用来源单据和 Receipt 做只读对账，无法唯一确认就转人工。
- 为什么 Run 没有在一个 PO Submit 完成后关闭？回答：Phase 10 是跨单据长任务，单 Action 完成不代表收货、开票和付款都完成；Run 终态要等后续 PlanStep 的事实确认。

### 10. 面试官可能追问的技术细节以及如何回答

- 为什么 P2P action 使用 schema v2？回答：保留 v1 Draft 历史可读性，同时让新动作的字段、审批和重检规则有明确版本边界。
- 为什么审批人和执行人必须绑定？回答：避免批准者看到一份内容、另一个会话执行另一份内容；执行前仍会重新验证身份、权限、状态和 digest。
- 为什么 ERP 返回成功但应用仍可能进入对账？回答：网络可能在业务提交后丢失响应，Transport 成功不等于业务回执已被确认。
- 为什么不让 Agent 直接提供税额或总账分录？回答：会计、税务和 Workflow 由 ERP/Frappe controller 权威计算与校验。
- 当前最重要的未完成证据是什么？回答：固定 ERP 上使用隔离发起人与独立审批人的 PO Submit 真实链路及其失败/恢复证据；当前状态为待验收。
