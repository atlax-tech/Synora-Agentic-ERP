## 1. 这个项目是什么

### 对外面试回答（默认采用）

Synora 是一个面向真实 ERP 采购场景的生产级 Agent 工程项目。它解决的是采购人员需要跨库存、未来需求、在途采购、开放采购单和供应商信息反复核对，容易漏查、重复采购，而且传统大模型方案缺少权限控制、过程审计和结果可信度的问题。

项目把自然语言采购目标接入 ERPNext/Frappe，在用户身份、公司、仓库和权限范围内，通过类型化工具网关读取 ERP 事实，再由确定性程序计算库存缺口、重复采购和风险分类，最后生成可解释、可追溯、可回退的采购分析结果。模型负责理解目标和解释结果，但不能绕过 ERP 权限、直接访问数据库或自行决定业务数量。

当前已经完成真实 ERPNext 环境中的只读采购分析链路，重点验证了身份透传、权限隔离、Typed Tool Gateway、确定性业务计算、Provider 失败回退、预算约束和审计数据流。后续会在审批、幂等、执行前状态重检、执行后读回和回执闭环具备证据后，逐步扩展到受控采购写入。

### 大白话业务解释与数据流

采购人员不需要再手工打开多个 ERP 页面拼接信息，而是提出一个采购分析目标，系统在其授权范围内查找事实并给出带依据的建议：

```text
自然语言采购目标
  -> Frappe 身份、公司/仓库和权限确认
  -> Typed Read-only Tool Gateway
  -> ERPNext/Frappe 事实
  -> 确定性库存与采购风险分析
  -> 结构化采购计划
  -> 模型解释或确定性回退
```

### 项目亮点、技术栈和架构

- ERPNext 仍是业务事实、权限、校验、Workflow、事务和审计的权威来源；Runtime 不能直连 MariaDB。
- 数量、金额、阈值和风险分类由确定性 Python 代码完成；模型输出必须经过结构和语义校验。
- Provider 超时、usage 缺失、输出超预算、数字不一致或风险语义反转时，系统不采用模型文本，回退到确定性摘要。
- 架构是 `ERPNext Desk -> Synora Frappe App -> Typed Gateway -> ERPNext/Frappe`，Frappe App 再调用独立的 `Agent Runtime -> Provider/Retrieval/Eval`。

| 层 | 当前技术/边界 | 选择原因 |
| --- | --- | --- |
| ERP | Frappe 16.31.0、ERPNext 16.32.3、MariaDB、Redis | 复用真实采购对象、权限和事务 |
| ERP 扩展 | Frappe Custom App、Python、Desk 页面 | 保留 ERP 登录态和业务入口，不修改上游核心 |
| Runtime | Python 3.14、FastAPI、Pydantic v2、HTTPX | 与 Frappe 解耦，严格解析跨边界数据 |
| Provider | DeterministicProvider + OpenAI-compatible BYOK | 可复跑、可替换并隔离密钥 |
| Retrieval | 版本化 Markdown + SQLite FTS5/BM25 | 可重建、可解释、可测量 |

当前边界是只读采购分析；Phase 4 执行内核尚未启动，Phase 6 才进入第一批 MR/PO Draft 受治理写入，完整采购单、收货、发票和付款写入属于后续阶段。面试中应说“当前完成了真实 ERP 集成的只读链路，正在按生产级门禁推进受控执行”，不能声称已经生产部署、已有客户或产生未经证实的效率收益。

## 2. 当前是否使用或规划 Multi-Agent

### 当前状态

当前**没有正式使用 Multi-Agent**。
Phase 3 是单 Agent/确定性编排基线，Phase 4 也只建立有界的单 Agent 执行内核。
仓库中没有已接入业务主线的 Planner、Reviewer 或 Agent Swarm。

### 未来规划

Multi-Agent 学习安排在 **Phase 9**，不是当前阶段，也不是必然进入业务主线。
计划中的实验包括 Supervisor、Peer-to-Peer、Hierarchical、managed-agent-as-tool 和显式 graph node，并优先评估：

```text
Procurement Planner
  -> typed handoff
Policy / Risk Reviewer
  -> 确定性 Policy、人工审批和 ERP Gateway
```

异常路径再研究 Reconciliation Agent。
所有 handoff 必须是版本化 typed state/event，带角色工具 allowlist、数据 scope、预算、超时、取消、共享状态版本和 correlation id。
自由聊天式 swarm 禁止。

### 为什么后置

单 Agent 是对照组。
没有单 Agent 的质量、安全、成本、延迟、恢复和 Trace 基线，就无法判断 Multi-Agent 是真正带来净收益，还是只增加了调用、Token、延迟和调试复杂度。

### 可能收益、代价与风险

可能收益：角色职责更清晰、上下文和工具权限可以隔离、Reviewer 可以提供独立检查、部分任务可以安全并行。

主要代价：更多模型调用、更高成本和延迟、更复杂的状态与故障定位、handoff 信息损失、循环争论和重复执行。

主要风险及控制：

| 风险 | 控制 |
| --- | --- |
| Reviewer 变成橡皮图章 | 独立证据、固定反例、不同权限和 A/B 评测 |
| 权限扩散 | 每个角色独立 allowlist 和 scope，Gateway 仍是最终边界 |
| 重复执行或死循环 | 幂等键、状态版本、最大步数、超时和取消 |
| 共享状态冲突 | typed state、版本检查、执行前重查 ERP |
| 技术为面试而采用 | 只有同任务净收益才进入业务主线，拒绝方案保留实验和证据 |

## 3. Function-calling / Tool-calling 当前和后续规划

这里必须区分两件事：

1. **Typed Tool Gateway**：系统代码调用哪些受控业务工具；
2. **模型 Tool Calling**：模型返回要调用哪个工具以及结构化参数。

### 当前已经有的能力

当前已有 6 个版本化、类型化、只读工具：

- `item.lookup`
- `supplier.lookup`
- `stock.projected`
- `demand.open`
- `material_request.open`
- `purchase_order.open`

Gateway 会依次执行工具名/版本 allowlist、输入 schema、Run 有效性、当前用户、公司/仓库 scope、ERP DocType 权限、分页/结果上限和结构化输出校验。
Provider 契约已经能描述 `tools` 并解析 `tool_calls`，但 Phase 3 的真实业务链路仍由确定性编排选择工具；模型没有自主选择 ERP 工具。

因此准确说法是：**项目已经使用 Typed Tool Gateway，也预留了 Provider-native Tool Calling 协议，但尚未在业务主线开放模型自主选工具。**

### Phase 4 的规划

Phase 4 将在当前用户的只读 allowlist 内，让模型根据第一次 Observation 选择第二个不同工具，并记录 Action/Observation/StopReason。
它必须同时防御：未知工具、非法参数、重复调用、无进展、token/成本/wall-clock 超预算、取消和错误重试。

模型提出调用不等于系统执行。未来任何写入仍要经过 typed parsing、权限/Policy、当前状态、人工审批、幂等、执行后 read-back 和 Receipt；Phase 4 本身不做写入。

## 4. 项目如何处理模型幻觉

项目不声称“消灭幻觉”，而是让幻觉不能直接变成业务事实、权限决定或 ERP 写入。

1. **确定性计算**：库存、需求、在途、缺口、重复采购和阈值由 Python 代码完成，模型不能计算采购数量或金额。
2. **权限隔离**：模型不能直连数据库；ERP 事实只能通过 Typed Gateway，Frappe 每次重检身份、Run、公司、仓库和 DocType 权限。
3. **职责限制**：Phase 3 的真实模型主要负责解释已经算好的计划，不负责创建业务动作。
4. **结构与语义校验**：输出必须可解析，文本中的数字必须来自确定性计划，不能反转“缺货/充足”或“重复采购/立即采购”等风险含义，Provider usage 和预算也必须满足契约。
5. **失败回退**：Provider 报错、超时、usage 缺失、输出/推理 token 超预算、数字编造或风险语义不一致时，模型文本不被采用，页面展示确定性摘要并记录回退原因。
6. **状态和副作用隔离**：Run 状态由确定性状态机改变；未来写入要再经过 Policy、审批、幂等、读回和 Receipt。
7. **检索内容不可信**：RAG 内容只能作为带来源的数据，不能改变 system instruction、权限、Policy 或工具 allowlist。

仍然存在限制：当前语义检查有关键词级局限，引用不保证结论一定正确，Provider 请求参数也不能追回已经产生的费用。因此系统依赖的是“确定性事实 + 权限边界 + 输出校验 + 失败回退 + 人工审批”，不是相信模型永远正确。

## 5. 是否设计了模型记忆

### 当前结论

当前**没有完整的用户级长期记忆模块**。已有的 Run 记录、分析结果和 FTS5 索引不能直接称为模型记忆：

- Agent Run 是一次受治理任务的身份、scope、目标、状态和审计记录；
- FTS5/BM25 是可重建的版本化知识检索缓存；
- ERPNext 是当前库存、订单和权限等业务事实的唯一权威来源。

### 当前和规划中的记忆层

| 层 | 含义 | 当前状态 |
| --- | --- | --- |
| Working Memory | 当前模型请求中的目标、计划、工具观察 | Phase 3 有限使用 |
| Episodic/Run Memory | 某次 Run 的目标、范围、状态、分析、计划和 correlation | 已有 Run/自有 DocType，但不会自动喂给未来任务 |
| Procedural Memory | 可版本化的采购 SOP、工具使用规则和 Skills | 有 curated source/规则基线；完整治理后置 |
| Semantic Memory | 可检索的 ERP 规则、权限基线和知识 | 已有 FTS5/BM25 基线，不是业务事实源 |
| Durable Workflow Checkpoint | 多步骤中断后从哪里恢复 | Phase 5 规划，当前未实现 |
| User Preference Memory | 用户偏好仓库、供应商或表达习惯 | 未实现，不能未经同意推断 |

完整 Memory/RAG/Contextual ERP Coach 演进安排在 **Phase 8**；
Multi-Agent 是 Phase 9。当前没有向量数据库、Embedding 用户画像、自动经验总结或跨用户共享记忆。

### 受治理的长期记忆召回链路（规划）

```text
用户登录并创建 Run
  -> Frappe 确认用户、公司、仓库和角色 scope
  -> 根据目标生成检索查询
  -> 按 permission_scope、ERP 版本和来源版本过滤
  -> FTS5 / vector / hybrid 召回候选
  -> 排序、去重、必要时压缩上下文
  -> 检查注入、来源冲突、过期和用户隔离
  -> 将内容与来源元数据放进模型上下文
  -> 模型生成带引用答案
  -> 确定性检查引用是否支持结论；不足则拒答或追问
  -> 保存检索版本、命中来源、回答和评测证据
  -> 用户反馈进入候选评测集，不直接污染权威知识库
```

### 当前已实现与未实现

已实现：版本化 curated source、SQLite FTS5/BM25、中文子串补充召回、`permission_scope` 过滤、来源/ERP 版本元数据和可重建索引。

尚未实现：Contextual ERP Coach 用户入口、完整角色到检索 scope 映射、vector/hybrid/rerank、Context Compression、引用支持性评测、用户偏好/情节记忆，以及记忆写入的同意、删除、保留期和纠错治理。

结论：当前项目有 Run 级任务状态和 FTS5 知识检索基线，但没有用户级长期记忆。实时库存、订单和权限永远必须重新查询 ERP，不能从记忆中当作当前事实读取。
