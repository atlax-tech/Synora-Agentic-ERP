# Synora 项目方向纠偏方案 V2

> 状态：`APPROVED / 用户已批准`
>
> 日期：2026-08-26
>
> 定位：Agent 开发岗位学习仓库 + 真实 ERP 业务实践载体
>
> 批准记录：2026-08-26 用户批准项目定位、同一仓库双层结构与 Phase 4–13 路线；本文是后续权威文档同步的方向依据，不代表后续阶段已实现或已启动。

## 1. 这次纠偏到底纠正什么

上一版的方向判断有一半是对的：当前 Synora 确实缺少真实的 Agent 决策循环，需要补 Tool Calling、ReAct、Plan-and-Execute、持久工作流、记忆、多 Agent 和轨迹评测。

但上一版的路线设计有三个严重问题：

1. 把用户点名的 Agent 关键词当成了完整岗位能力地图，漏掉低代码、框架设计、上下文工程、协议、Agent Eval、Agentic RL、Web/GUI Agent、自进化、后训练和 AI Infra 等知识；
2. 把五个项目仓库当作横向功能参考，没有理解它们在学习上是“案例实验室 → 通用执行内核 → 企业级系统”的递进关系；
3. 只重排 Phase 4，没有重新设计 Phase 5 及以后阶段，结果会把 Phase 4 变成一个范围失控的大包，后续阶段又接不住纠偏后的架构。

V2 不再把目标设成“用最少技术交付一个可商业化采购产品”，而是：

> **通过一个真实 ERP 采购场景，系统学习、实现、比较和复盘 Agent 开发岗位的重要知识；核心链路必须能运行，暂不适合业务主线的知识也必须通过实验、取舍记录和面试讲解留下学习证据。**

这不是照抄某个开源项目。更准确的做法是“学习转译”：先理解原项目为什么这样设计，再把同一问题换成 Synora 的采购任务实现，最后用测试和运行轨迹说明哪些设计成立、哪些不成立。

## 2. 项目的新定位：同一仓库中的业务应用层与教学实验层

Synora 不拆成两个仓库，也不建立两条长期开发分支。业务应用层和教学实验层共存于同一仓库、同一开发主线，共用契约、评测、日志和面试证据。

### 2.1 业务应用层：真实 ERP 主线

目标是构建一个能在真实 ERPNext 上工作的“受治理采购运营 Agent”：

```text
自然语言目标
  → Agent 识别任务和缺失条件
  → 动态选择只读工具获取 ERP 事实
  → 根据观察调整计划
  → 生成带证据的 ProposedAction
  → 人工审批
  → 确定性 Executor 执行 ERP 动作
  → read-back、回执和异常对账
```

业务主线负责证明：Agent 不是只会聊天，而是参与了真实任务的观察、决策、行动和反馈闭环。

### 2.2 教学实验层：Agent 学习实验室

Phase 4 起按需新增 `labs/agent_patterns/`，每个实验都使用采购或 ERP 示例，但不要求直接进入业务链路。实验包括：

- 手写 Direct、ReAct、Plan-and-Execute 和 Reflection；
- 原生 Function Calling 与框架 Tool Calling 对比；
- smolagents 风格的最小多步执行器；
- LangGraph checkpoint、interrupt、time travel 和子图；
- MCP、A2A、ANP 的最小协议实验；
- Working/Episodic/Semantic/Procedural Memory；
- Router、Supervisor、Peer-to-Peer、Planner/Reviewer 多 Agent；
- Web Agent、GUI Agent 和多模态观察实验；
- Prompt/Skill 自优化、失败轨迹学习和离线自进化；
- SFT、DPO、Agentic RL 的小数据或离线 Notebook 实验；
- 模型路由、降级、缓存、并发、评测和可观测性。

实验室的价值不是多放几个 Notebook，而是形成四件套：

1. 可运行的最小实现；
2. 同一任务的对照实验；
3. 失败案例和调试记录；
4. “为什么主线采用或不采用”的 ADR/学习笔记。

### 2.3 两层怎样避免互相割裂

每个知识点都按同一顺序学习：

```text
原理讲解
  → 最小实验
  → 开源源码对照
  → Synora 业务魔改
  → 测试与 Trace
  → 取舍复盘
  → 面试追问
```

实验室先帮助理解，业务主线再证明工程能力。即使某项技术最终不进入业务主线，用户仍然有代码、实验结果和取舍理由，能够在面试中讲清楚。

## 4. `hello-agents` 给出的完整岗位知识地图

`hello-agents` 的价值不只是教 ReAct。它实际上覆盖了 Agent 开发从基础到进阶的完整知识树。Synora 应按依赖关系学习，而不是按关键词出现次数学习。

### 4.1 L0：大模型与 Agent 基础认知

来源：第 1–3 章。

必须掌握：

- Agent 与普通 LLM、Workflow、规则系统的区别；
- 感知、决策、行动、环境反馈组成的闭环；
- 任务环境、可观察性、确定性/随机性和动态性；
- Transformer、token、上下文窗口、采样参数、模型选择；
- 模型幻觉为什么是生成机制的结果，而不只是“提示词没写好”；
- Workflow 和 Agent 不是二选一，真实系统通常混合使用。

Synora 的学习证据：用同一采购问题分别实现规则 Workflow、Direct LLM 和 Agent，并指出三者的主体、状态、行动空间和反馈来源。

优先级：`必须先学`。如果这层说不清，后面的框架使用只会变成 API 拼装。

### 4.2 L1：经典 Agent 范式与工具调用

来源：第 4 章、第 7 章、`code/chapter4`、`code/chapter7`。

必须掌握：

- Direct Generation：一次模型调用直接回答；
- ReAct：Reason/Action/Observation 循环；
- Plan-and-Solve / Plan-and-Execute：先拆任务，再逐步执行和重规划；
- Reflection：生成、评审、修改的迭代；
- Function Calling：模型输出结构化工具名与参数；
- Tool Registry、schema、描述、调用、结果回填和错误传播；
- SimpleAgent、ReActAgent、ReflectionAgent、PlanAndSolveAgent、FunctionCallAgent 的共同接口和差异。

Synora 的学习证据：先手写最小循环，再使用现成框架实现同一任务；保留工具选择错误、参数错误、重复调用和提前结束的 Trace。

优先级：`最高`。这是 Phase 4 的主题，但 Phase 4 只负责这一层和必要评测，不再吞下所有后续能力。

### 4.3 L2：框架、状态与工作流编排

来源：第 5–7 章。

必须掌握：

- Coze、Dify、FastGPT、n8n 等低代码平台的节点、工作流、知识库和集成思路；
- AutoGen 的对话协作、AgentScope 的工程化、CAMEL 的角色协作、LangGraph 的显式状态图；
- “涌现式协作”和“显式控制”的取舍；
- State、Node、Edge、条件路由、循环、子图、checkpoint 和 interrupt；
- 为什么路由、审批、幂等和金额规则通常不应交给自由文本判断；
- 自建 Agent 框架时的 LLM 适配层、消息模型、Agent 基类和 Tool Registry。

低代码平台不会被简单排除。实验室要做一次低代码采购流程复刻，并与代码版比较版本控制、可测试性、可观测性、权限和部署成本。这样面试时既能讲平台，也能讲为什么核心链路采用代码实现。

优先级：`高`。在理解手写循环后进入 Phase 5。

### 4.4 L3：Memory、RAG 与上下文工程

来源：第 8–9 章。

必须掌握：

- Working、Episodic、Semantic、Procedural/Perceptual Memory 的定义与边界；
- 记忆写入、提取、检索、整合、遗忘、纠正和权限隔离；
- RAG 的 ingestion、chunk、embedding、召回、混合检索、rerank、引用和评测；
- Memory 与 RAG 的区别：前者保存任务/用户经验，后者连接外部知识；
- 上下文是注意力预算，不是“窗口还能塞多少字”；
- GSSC：Gather、Select、Structure、Compress；
- JIT context、结构化笔记、摘要、归档和上下文腐蚀。

Synora 的学习证据：库存等实时事实必须调用 ERP；历史处理经验可以从 episodic memory 召回；SOP 从 RAG 召回；Prompt/Skill 从 procedural layer 加载。四种来源在 Trace 中必须可区分。

优先级：`高但后置于可靠执行循环`。上下文与 Skills 安排到 Phase 7，Memory/RAG 单独安排到 Phase 8，避免在 Agent 还不会稳定使用工具时先堆向量库。

### 4.5 L4：Agent 协议与多 Agent

来源：第 6、10、13、14 章。

必须掌握：

- MCP 解决 Agent 与工具/资源的标准连接；
- A2A 解决独立 Agent 的能力发现、长任务状态和协作；
- ANP 面向更开放的 Agent 网络、发现和路由；
- Supervisor、Peer-to-Peer、Hierarchical、Router、Handoff 和共享状态；
- typed handoff、角色权限、超时、取消、冲突裁决和结果聚合；
- TODO-driven research、并行 fan-out/fan-in 和多角色计划。

Synora 的学习证据：先做同进程 Planner/Reviewer，再做 MCP 工具服务和最小 A2A Agent Card/Task 实验；ANP 保留协议实验和选型说明，不必为了展示搭建虚假的开放网络。

优先级：`单 Agent 稳定后必学`，安排到 Phase 9。

### 4.6 L5：评测、安全与生产工程

来源：第 12 章、`build_a_product_agent` 第 5 章、`hello-agents` 实践踩坑扩展。

必须掌握：

- BFCL 式 simple、multiple、parallel、irrelevance 工具调用评测；
- GAIA 式多步任务评测；
- 金标准、轨迹断言、LLM-as-Judge、pairwise win rate 和人工抽检；
- 功能、质量、安全、鲁棒性、性能、长稳、灰度、影子和 A/B 测试；
- Prompt injection、间接注入、越权工具、敏感信息、记忆污染；
- Trace、结构化日志、token/成本、工具错误和 stop reason；
- async、流式接口、session/tenant 隔离、重试/降级、限流和模型路由。

优先级：`贯穿每一阶段`，不是等项目最后才补。Phase 4 建立第一版 Eval Harness，以后每个阶段扩展。

### 4.7 L6：高级方向，不因当前业务不需要而删除

来源：第 11 章及 GUI Agent、Web Agent、Skills、自进化、后训练扩展章节。

需要学习并留下实验的内容：

- Agent Skills 与 Tool、Prompt、Workflow、MCP 的关系；
- GUI Agent 的视觉观察、元素定位、动作生成和安全风险；
- Web Agent 的页面观察、DOM/视觉动作、登录态、反爬和异步任务；
- 失败轨迹沉淀 Skill、离线 Prompt 优化和带版本回滚的自进化；
- SFT、DPO、Best-of-N/Rerank、奖励设计和 Agentic RL；
- 多模态输入、代码执行 Agent 和环境 sandbox；
- 本地模型、vLLM/SGLang、模型路由和推理基础设施。

这些内容安排到独立高级实验阶段。它们不必全部进入采购主线，但每项都要回答：解决什么问题、最小实现是什么、风险是什么、什么真实场景值得采用、为什么 Synora 主线此刻采用或不采用。

## 5. 从知识地图得到的学习优先级

不能按照“越新越高级越先学”排序。正确顺序由依赖关系决定：

| 顺序 | 学习主题 | 为什么排在这里 |
|---:|---|---|
| 1 | Agent/Workflow/LLM 边界 | 先知道什么问题值得 Agent 化 |
| 2 | Tool schema 与原生 Function Calling | Agent 必须先能可靠行动 |
| 3 | 手写 ReAct 与停止条件 | 看清框架替你做了什么，也亲手踩循环和解析错误 |
| 4 | Eval、Trace 和安全基线 | 没有测量就无法比较后续架构 |
| 5 | 框架化状态图、checkpoint、HITL | 把一次循环变成可恢复的长任务 |
| 6 | Plan-and-Execute、Prompt/Context、Skills | 处理复杂任务并控制上下文和流程知识 |
| 7 | 受治理写入、幂等、回读和对账 | 证明 Agent 真正改变业务世界且不会乱写 |
| 8 | Memory 与 RAG | 执行内核稳定后再增加跨会话经验与外部知识 |
| 9 | Multi-Agent 与 MCP/A2A | 单 Agent 基线存在后才能证明拆角色是否有收益 |
| 10 | 完整业务生命周期 | 把前面能力用于更长、更危险的真实任务 |
| 11 | Web/GUI、自进化、后训练、Agentic RL | 先有真实失败轨迹和评测集，训练与优化才有对象 |
| 12 | AI Infra、部署和最终系统评测 | 用完整链路讨论性能、扩展、降级和运维 |

## 6. `build_a_product_agent` 提炼出的工程路线

这个仓库不应被当成“照着文档搭一套中间件”教程。它最有价值的是提醒我们：Agent 从 Demo 到可用系统要连续回答一组工程问题。

### 6.1 九个工程门

1. **任务门**：任务成功是什么，是否真的需要 Agent？
2. **协议门**：模型、工具、Agent、前端怎样交换 typed data？
3. **状态门**：session、tenant、run、checkpoint 和业务状态由谁拥有？
4. **工具门**：schema、超时、权限、重试、幂等、返回预算和错误语义是什么？
5. **编排门**：Direct、Workflow、ReAct、Plan-and-Execute、HITL 怎样路由？
6. **上下文门**：短期记忆、长期记忆、RAG、工具定义如何分配 token？
7. **可靠性门**：并发、限流、降级、取消、恢复、回滚和对账怎样实现？
8. **评测门**：功能、轨迹、质量、安全、性能和成本怎样持续回归？
9. **运维门**：日志、trace、模型路由、部署、健康检查、灰度和故障切换怎样落地？

这九个门会成为每个后续 Phase 的通用模板，而不是只在最终阶段检查。

### 6.2 需要批判吸收的地方

阅读工程资料本身也要有判断力：

- “共享状态必须 Redis”不是普遍真理。单实例、数据库事务已经满足需求时，引入 Redis 可能只增加一致性问题；应由并发模型和性能证据决定。
- “一个系统一个通用 `**kwargs` 工具”会减少工具数量，但也可能牺牲 schema 清晰度、权限最小化和静态验证。Synora 的 ERP 工具应继续使用细粒度 typed contract。
- “工具错误不要抛异常，全部返回文本”适合让模型理解部分业务失败，但系统错误仍需要结构化 error code、retryability 和审计；不能把所有异常降成自然语言。
- “某框架/数据库/推理引擎一定最好”只能看作作者在特定假设下的建议。Synora 必须写出自身约束、候选方案、测量结果和决定。
- 文档里的代码主要用于说明概念。未经运行、并发、失败和安全测试，不能直接称为生产实现。

项目要培养的不是背“最佳实践”，而是能解释最佳实践成立的前提，以及它在什么情况下会失效。

## 7. 三个项目仓库怎样形成由浅入深的工程学习

### 7.1 第一层：`GenAI_Agents`——案例实验室

它最适合快速观察“一个 Agent 模式如何服务具体任务”。建议按下面顺序选案例做复刻和改造：

| 学习层 | 代表 Notebook | 能学到什么 | Synora 魔改任务 |
|---|---|---|---|
| 单次生成 | `simple_question_answering_agent` | Prompt、chain、输入输出 | 采购政策解释 baseline |
| 工具 Agent | `task_oriented_agent` | Structured Tool、AgentExecutor、`max_iterations` | 动态查询库存或在途 |
| 状态图 | `customer_support_agent_langgraph` | State、node、conditional edge | 采购异常分类与路由 |
| 记忆 | `memory-agent-tutorial` | episodic/semantic/procedural memory namespace | 历史采购处置经验召回 |
| HITL | `HR_AI-Assistant` | MemorySaver、interrupt、人工复核 | MR Draft 审批中断 |
| 计划/并行 | `ClauseAI` | structured plan、`Send` fan-out、聚合 | 多物料并行风险分析 |
| 有界反思 | `social_media_publishing_agent...` | review/revise loop、最大轮数、idempotency key | 计划审查与一次修订 |
| 多 Agent | `multi_agent_collaboration_system` | 专门角色与结果汇总 | Planner/Reviewer 协作 |
| 自改进 | `self_improving_agent` | 生成、反思、学习闭环 | 离线 Prompt/Skill 候选优化 |
| Agent 测试 | `e2e_testing_agent` | 图状态、验证、错误反馈 | Agent 轨迹验收器 |

每次复刻必须指出 Notebook 为了教学省略了什么，例如持久数据库、用户隔离、权限、恢复、成本、安全或真实服务测试。省略项不是一句“不能用于生产”带过，而是下一层学习的入口。

### 7.2 第二层：`smolagents`——读懂一个通用执行内核

`smolagents` 的 `MultiStepAgent` 把核心循环写得足够集中，适合源码学习：

```text
初始化 task 和 memory
  → 可选 planning step
  → 创建 ActionStep
  → 模型生成 tool call 或 final_answer
  → 执行并保存 observation/error/token/timing
  → final_answer_checks
  → 未结束则 step + 1
  → 超过 max_steps 后生成受限最终结果
```

需要亲手追踪的源码概念：

- `max_steps` 为什么是必要但不充分的停止条件；
- `planning_interval` 怎样支持初始计划和周期性重规划；
- `AgentMemory` 怎样保存 Task、Planning、Action 和 FinalAnswer；
- `ToolCallingAgent` 怎样把 tools 和 managed agents 暴露给模型；
- `final_answer_checks` 怎样阻止不合格答案被接受；
- `step_callbacks` 怎样接入观测和自定义守卫；
- `interrupt()` 是进程内终止，不等于跨进程 durable resume；
- `managed_agents` 被包装成工具的优点和权限风险。

Synora 不只“参考”它，而要在实验室实现一个约 200–300 行的采购版 MiniStepAgent，再与 smolagents 和 LangGraph 版本跑同一评测集。这样用户能解释执行内核，而不是只会调用 `agent.run()`。

### 7.3 第三层：`deer-flow`——企业级系统怎样把能力拼成产品

deer-flow 的学习重点不是某个 Prompt，而是系统层次：

- Gateway、Runtime、Frontend、Sandbox、Persistence 和 Harness 的边界；
- lead agent 通过 middleware chain 叠加 thread、upload、sandbox、summary、todo、clarification 等能力；
- loop detection 不只限制总步数，还检测相同工具参数和工具频率；
- token budget、tool output budget、模型 finish reason 和 stop reason 形成多层停止治理；
- subagent 同时限制单轮并发和整次 Run 的总委派量；
- checkpoint、run journal、worker ownership、shutdown drain 和 recovery 共同处理长任务；
- skills 有发现、加载、启停、冲突、来源和工具策略；
- memory 有用户/Agent scope、存储、召回、shutdown 和后端适配；
- SSE 把工具、子任务、artifact 和状态变化展示给前端；
- 大量测试覆盖中间件顺序、隔离、恢复和边界行为。

Synora 要把这些设计翻译成 ERP 场景：

| deer-flow 问题 | Synora 对应问题 |
|---|---|
| thread isolation | Run、用户、公司和仓库范围隔离 |
| sandbox/tool policy | ERP capability allowlist 与 proposal/write 分离 |
| loop/token middleware | 每 Run 步数、重复调用、token、成本和时间门禁 |
| checkpoint/run recovery | 审批中断、进程重启、取消、过期和恢复 |
| skill activation | 采购 Skill 版本、来源和工具白名单 |
| subagent budget | Planner/Reviewer/Reconciliation 的并发和总调用预算 |
| read-before-write | snapshot/digest/current-state recheck 后才允许执行 |
| tool receipt | ERP write read-back、ExecutionReceipt 和 reconciliation |

这一步的目标是读懂企业级设计怎样应对真实故障，再用 Synora 自己的领域模型实现，而不是复制 deer-flow 的通用 shell、文件系统或浏览器工具。

## 8. 纠偏后的核心架构

### 8.1 四个责任层

```text
Frappe / ERPNext
  身份、角色、公司/仓库权限、业务事实、Workflow、事务、最终审计

Synora Control Plane
  Run、Capability、Policy、Approval、Idempotency、Executor、Receipt、Reconciliation

Agent Runtime
  Router、ReAct、Planner、Replanner、Context、Memory、Skills、Model、Budget、Trace

Learning & Eval Plane
  labs、golden tasks、trajectory assertions、red team、benchmark、interview evidence
```

### 8.2 三种执行模式共存

| 模式 | 适用任务 | 例子 |
|---|---|---|
| Direct / deterministic Workflow | 答案固定、无探索、要求低成本高确定性 | 显示已有 Run 状态、重算缺货数量 |
| Bounded ReAct | 需要根据观察决定下一步，但目标较短 | 先查需求，再根据结果决定查库存还是已有 PO |
| Plan-and-Execute + inner ReAct | 多步骤、有依赖、可能暂停或重规划 | 分析多个物料并准备 MR Draft |

路由器必须可评测。第一版可以使用确定性特征 + 小模型结构化分类，不能只凭几个关键词，也不能让复杂模型路由成为新的黑盒。

### 8.3 写入权怎样设计

“Agent 有业务价值”不等于“模型可以自由写 ERP”。合理的真实闭环是：

1. 模型动态调查并生成 typed `ProposedAction`；
2. Policy 重新计算数量、权限、重复采购、snapshot 和风险；
3. 人工看到计划、证据和后果后批准；
4. deterministic Executor 使用批准时绑定的 action digest 执行；
5. 写后 read-back；
6. 结果不确定时进入 reconciliation，不盲重试。

模型拥有受限的调查和规划权，系统保留最终授权和副作用控制。这仍然是 Agent，因为模型真实参与了“下一步做什么”和“根据环境怎样调整”，而不是只润色文案。

## 9. 所有后续阶段重新规划

Phase 0–3 不删除。它们被重新解释为“真实 ERP、安全边界、typed tools 和 deterministic baseline”，是后续 Agent 学习的地基，但不能单独代表完整 Agent 项目。

原 Phase 4–8 整体废止并重新映射为 Phase 4–13。每阶段只解决一组相邻问题，并同时交付业务主线、学习实验、评测证据和用户 Assignment。

### Phase 4 — Agent 执行内核与原生 Tool Calling

学习目标：真正理解 Agent 怎样循环，而不是先学框架 API。

业务主线：

- 让模型在当前用户只读 allowlist 内动态选择现有 ERP tools；
- 实现 Action/Observation trace、structured final answer 和 stop reason；
- 继续由确定性代码计算数量和阈值。

学习实验：

- 手写 Direct、ReAct、Plan-and-Solve、Reflection；
- 实现采购版 MiniStepAgent；
- 与 smolagents `ToolCallingAgent` 跑同一任务；
- 比较 prompt-based ReAct 与 provider-native tool call。

工程与评测：

- tool schema、参数校验、unknown tool、tool error、output budget；
- max steps、重复参数、无进展、token、成本和 wall-clock 停止条件；
- 建立第一版 golden task、BFCL 风格工具评测和 Trace viewer。

用户 Assignment：亲手完成一个重复工具调用守卫，并解释为什么只有 `max_steps` 不够。

出口证据：至少一个真实任务需要模型根据第一次 observation 选择第二个不同工具；循环攻击能够被明确的 stop reason 截停；Direct/ReAct/smolagents 三组结果可比较。

### Phase 5 — 持久工作流与 Plan-and-Execute

学习目标：把一次性循环升级为可暂停、可恢复、可调试的长任务。

业务主线：

- typed AgentState、PlanStep、依赖、重规划和 clarification；
- LangGraph checkpoint、interrupt、resume、cancel、expiry 和 crash recovery；
- Run 页面展示计划、步骤、工具、观察摘要和停止原因；
- Runtime 内部认证和短期 capability。

学习实验：

- AutoGen/CAMEL 对话协作与 LangGraph 显式图对比；
- 用 Dify/n8n 复刻一个只读采购流程，并与代码版比较；
- 比较图内状态、checkpoint 状态和 Frappe 业务状态；
- 比较固定 Workflow、ReAct 子图和 Plan-and-Execute 子图。

工程与评测：

- checkpoint 与 Frappe 业务状态分离；
- 节点输入输出 schema、版本升级和兼容；
- 恢复不得重复已完成工具调用；
- 无进展、状态漂移、并发恢复和取消竞态测试。

用户 Assignment：手工让 Agent 在第二步崩溃，画出 checkpoint、业务状态和恢复后的数据变化。

出口证据：进程重启后可从最近安全点恢复；取消/过期后不能继续调用工具；Plan-and-Execute 相比 ReAct 在复杂任务上有可解释的质量/成本数据。

### Phase 6 — 受治理的第一批 ERP 行动

学习目标：证明 Agent 能产生真实业务动作，同时掌握 HITL、授权、幂等和对账。

业务主线：

- 完成 `approval-workflow-mapping` 真实取证；
- versioned ProposedAction、PolicyDecision、ApprovalDecision、ExecutionReceipt；
- MR Draft，然后是 PO Draft；
- stale approval、current-state recheck、digest、idempotency reservation；
- write、read-back、response lost 和 reconciliation；
- 审批/拒绝/修改/过期 UI。

学习实验：

- 对照 `GenAI_Agents` HR HITL 和社交发布案例；
- 比较 `interrupt_before` 与领域审批状态机；
- 实现一次重复请求、响应丢失和人工对账演练。

工程与评测：

- 开放式 ReAct 循环不可直接获得 ERP write tool；
- 未授权、未审批、过期、状态漂移和重复写必须为 0；
- 每次写入都必须有可验证回执。

用户 Assignment：亲手设计一组 idempotency key/digest 冲突用例，并解释为什么 HTTP 200 不代表业务成功。

出口证据：Buyer 目标 → Agent 调查 → ProposedAction → 人审 → 单次 MR/PO Draft → read-back/Receipt 的完整真实链路。

### Phase 7 — Prompt、Context Engineering 与 Skills

学习目标：学会管理模型真正看见的信息，并把业务经验封装为可版本化能力。

业务主线：

- Prompt 的边界层、决策层、恢复层、输出契约和版本/hash；
- GSSC ContextBuilder、JIT context、summary、structured notes 和 token budget；
- `replenishment-analysis`、`duplicate-purchase-check`、`material-request-draft`、`reconciliation` Skills；
- Skill provenance、allowed tools、自由度等级、渐进式加载和回归评测。

学习实验：

- 对同一采购任务做 system prompt 单变量 A/B；
- 实现 Gather/Select/Structure/Compress 四阶段 ContextBuilder；
- 实现一个带三级渐进披露的 SKILL；
- 比较 Tool、Prompt、Skill、Workflow 和 MCP 的职责。

工程与评测：

- 关键安全约束不依赖动态历史，压缩后仍必须存在；
- Skill 不能扩展当前 capability allowlist；
- 记录每轮实际注入了什么、为什么选择、压缩丢失了什么；
- 评估上下文相关性、完整性、信息密度、token 和任务成功率。

用户 Assignment：亲手编写一个采购 Skill，再故意加入一条会诱发错误工具选择的冗余指令，通过 Trace 找出并修复。

出口证据：同一任务能复现 Prompt/Context/Skill 版本，精简上下文后质量不退化且 token 有可测变化；恶意 Skill 指令不能扩权。

### Phase 8 — Memory、RAG 与 Contextual ERP Coach

学习目标：让 Agent 跨会话复用经验和外部知识，同时不把过期事实当真。

业务主线：

- Working、Episodic、Semantic、Procedural 四层记忆；
- memory candidate、审核、版本、过期、纠正、删除和 scope；
- SOP/ERP 文档 RAG：FTS5 baseline → embedding → hybrid → rerank 对照；
- Contextual ERP Coach、引用、冲突和拒答。

学习实验：

- 复刻 `memory-agent-tutorial` 的 namespace 和三类记忆；
- 实现短期裁剪、长期提取、召回、去重、整合和遗忘；
- 对同一语料比较 BM25、vector、hybrid 和 rerank；
- 比较 Memory 与 RAG 的写入来源、生命周期和可信度。

工程与评测：

- 实时库存、订单和权限永远从 ERP 查询；
- 跨公司、跨用户和无权限记忆不可见；
- 记忆/RAG 文本不能扩展 tool allowlist；
- 评估 recall、precision、groundedness、citation、freshness、permission 和 injection。

用户 Assignment：亲手构造一条恶意历史记忆，设计它从候选写入到召回拦截的完整测试。

出口证据：Agent 能召回经审核的历史经验和 SOP，但会重新查询实时 ERP 事实；跨租户和过期记忆安全失败。

### Phase 9 — Multi-Agent、MCP 与 A2A

学习目标：理解何时拆 Agent、怎样通信、怎样限制协作成本和错误传播。

业务主线：

- Planner → Policy/Risk Reviewer；
- 异常时才启动 Reconciliation Agent；
- typed handoff、独立 tool allowlist、共享/私有 state、一次修订上限；
- 单 Agent vs 多 Agent A/B。

学习实验：

- Supervisor、Peer-to-Peer、Hierarchical 三种最小实现；
- 把一个只读 Synora capability 暴露为本地 MCP server；
- 实现最小 A2A Agent Card、Task、status、cancel；
- ANP 做服务发现/路由概念实验与选型报告；
- managed-agent-as-tool 与显式 graph node 对比。

工程与评测：

- 限制子 Agent 单轮并发、整 Run 总量、token、时间和深度；
- 防止 Planner 与 Reviewer 相关性幻觉；
- 子 Agent 失败、超时、取消、部分结果和冲突裁决；
- A/B 比较质量、安全、延迟、成本和复杂度。

用户 Assignment：分别扮演 Planner 和 Reviewer，调试一次证据冲突，并决定该修订、拒绝还是交人。

出口证据：至少一个角色在同一评测集上有可测净收益；没有收益的角色也保留完整拒绝证据和实验代码，而不是删除学习成果。

### Phase 10 — 完整 P2P 运营 Agent

学习目标：把前面的 Agent 能力用于更长、更危险、跨单据的真实企业流程。

业务主线：

- PO Submit；
- Purchase Receipt 与部分收货；
- Purchase Invoice 与部分开票；
- Payment 相关受控流程；
- 跨单据计划、审批、执行、状态漂移、取消和对账；
- 长任务中断和人工接管。

学习实验：

- 为不同业务阶段比较单 Agent、固定 Workflow 和多 Agent；
- 研究事件驱动、消息队列、scheduled task 和 long-running task；
- 设计 failure saga，但不把 ERPNext 事务语义伪装成通用分布式事务。

工程与评测：

- 会计、税务、权限和 Workflow 继续由 ERP/Frappe 权威控制；
- 每种副作用独立幂等和回读；
- 端到端 Trace 能关联 Plan、Action、Approval、Receipt 和人工介入。

用户 Assignment：选择一次部分收货或部分开票，画出正常、重复、取消和响应丢失四条时序图。

出口证据：完整 P2P 主路径和主要异常路径可在真实 ERP 环境复跑。

### Phase 11 — Web Agent、GUI Agent 与多模态观察

学习目标：理解 Agent 除 API Tool Calling 以外怎样感知和操作数字环境。

学习实验：

- Web Agent：在隔离测试页面完成采购页面观察和受控操作；
- 比较 DOM、Accessibility Tree、截图视觉和混合观察；
- GUI Agent：元素定位、坐标动作、动作确认和失败恢复；
- 多模态：读取采购单截图或错误截图并生成结构化观察；
- 比较 API Agent、Web Agent 和 GUI Agent 的稳定性、成本和权限边界。

主线边界：

- Web/GUI 自动化只运行在隔离测试环境，不用来绕过 ERP API、Workflow 和权限；
- 任何高风险动作都要求明确确认和可观察回执；
- 页面变化、弹窗、登录失效和视觉误定位必须进入失败集。

用户 Assignment：亲手完成一个只读 Web Agent 任务，并回答 DOM 定位与视觉定位各自在什么情况下会失败。

出口证据：API/Web/GUI 三种方式对同一只读任务有可复现对照；至少保留一次页面变化导致的失败复盘。

### Phase 12 — 自进化、后训练与 Agentic RL

学习目标：使用前面阶段积累的真实失败 Trace 和评测集优化 Agent，而不是为了训练而训练。

学习实验：

- Reflection 和 Best-of-N + verifier baseline；
- 从失败 Trace 生成 Skill/Prompt 候选，在离线评测通过后人工晋级；
- SFT：用小型、脱敏、可审计数据学习结构化工具选择或计划格式；
- DPO：构造通过硬门禁的偏好对并验证偏好数据质量；
- Agentic RL：在模拟采购环境中设计 state、action、reward 和长期回报；
- 比较 Prompt、RAG、rerank、SFT、DPO、RL 分别解决什么问题。

工程边界：

- 自进化只能产出候选版本，必须可回滚、可比较、可审计；
- train/eval 数据隔离，禁止把评测答案泄漏进训练；
- 不为了“训练过模型”虚构收益；没有统计优势时保留失败结论。

用户 Assignment：亲手审查一组好/坏轨迹并设计奖励函数，解释奖励黑客和 Judge 偏差可能怎样发生。

出口证据：至少完成一个 Prompt/Skill 优化和一个模型适配实验；必须包含基线、数据审计、离线评测和一个没有收益或出现副作用的结果。

### Phase 13 — AI Infra、系统硬化与毕业作品

学习目标：把 Agent 能力整理成一个可部署、可观测、可评测、可面试讲解的完整工程。

业务与工程：

- async/streaming/session isolation、连接池、限流和 backpressure；
- provider/model router、fallback、circuit breaker、cache 和成本预算；
- 本地模型与 BYOK 对照，理解 vLLM/SGLang/Ollama 的适用边界；
- tracing、metrics、logs、dashboard、token/cost/latency；
- shadow、canary、A/B、长稳、并发、恢复和安全演练；
- Docker/进程守护/健康检查；K8s 做部署设计或本地实验，不虚构生产集群经验；
- 全阶段 requirement-to-code-to-test traceability。

学习成果：

- 一条完整 ReAct Trace；
- 一次循环事故复盘；
- 一次 checkpoint 恢复；
- 一次 stale approval 拒绝；
- 一次幂等/对账；
- 一次记忆污染拦截；
- 一次多 Agent 冲突；
- 一次模型或 Prompt A/B；
- 一个高级技术不采用案例；
- 用户亲手完成的 Assignment、代码 Review 和面试问答。

出口证据：完整 Rubric、风险评估、独立对抗审查和真实浏览器验收通过后，才形成最终 README、简历表述和项目讲解。

## 10. 评测不是最终阶段，而是开发方法

### 10.1 四层评测

| 层 | 评什么 | 典型断言 |
|---|---|---|
| Component | tool、router、memory、retriever、policy | schema、参数、权限、排序、error code |
| Trajectory | Agent 每一步是否合理 | 工具选择、顺序、重复、重规划、stop reason |
| Task | 业务目标是否完成 | 正确识别风险、生成有效 proposal、完成回读 |
| System | 真实链路是否安全稳定 | 并发、恢复、成本、延迟、注入、越权、写入幂等 |

### 10.2 每个阶段都必须扩展同一 Eval Harness

至少记录：

- 输入、用户/公司/仓库 scope；
- model、prompt、skill、tool schema 和代码版本；
- 每一步 tool call、canonical args、observation digest；
- plan/replan/clarification/stop reason；
- token、模型调用数、工具调用数、耗时和估算成本；
- 最终结构化结果、引用、approval 和 receipt；
- golden assertion、规则评分、LLM judge 和人工抽查结果；
- 失败样例是否进入 regression set。

### 10.3 LLM-as-Judge 不能单独决定通过

LLM Judge 适合评解释质量、完整性和风格，不适合独立判断权限、金额、工具参数、幂等和 ERP 状态。这些必须由确定性断言、真实系统读回和人工抽检决定。

## 11. 学习取舍怎样记录，而不是怎样删除

后续每项技术使用统一的 Adoption Card：

| 字段 | 必须回答 |
|---|---|
| Problem | 它解决什么具体问题？ |
| Preconditions | 什么规模、数据、风险或团队条件下问题成立？ |
| Minimal Lab | 用户亲手完成的最小实验是什么？ |
| Alternatives | Workflow、单 Agent、其他框架或确定性代码能否解决？ |
| Evidence | 同一数据集上的质量、成本、延迟、安全和复杂度结果是什么？ |
| Decision | 主线采用、仅实验室保留、延期还是拒绝？ |
| Real-world Use | 哪类真实项目会选择它？ |
| Interview Answer | 面试官追问时怎样用本项目证据回答？ |

因此，“当前项目不适合某技术”不再意味着仓库里完全没有它，而意味着：实验做过、证据存在、主线取舍可解释。

## 12. 用户参与方式必须成为阶段出口条件

每个阶段至少包含：

1. 一次用户亲手编码 Assignment；
2. 一次用户手工运行和观察 Trace；
3. 一次用户先回答、导师再追问的设计讲解；
4. 一次真实 Bug/失败路径复盘；
5. 一组基于本阶段代码的面试问答。

Assignment 必须说明：业务背景、为什么做、代码入口、输入输出、完成标准、测试、不应修改的边界、提示梯度和面试追问。用户没有完成时记录“待练习”，不能由 Coding Agent 代做后声称用户掌握。

项目日志继续原文保留用户问题、质询和卡点，并记录导师解释、代码证据、最终结论和复习动作。

## 13. 风险预测

### 13.1 工程风险

| 风险 | 为什么会发生 | 控制方式 |
|---|---|---|
| Agent 循环失控 | 模型重复工具或错误重试 | 多层 loop/no-progress/token/time/cost guard |
| checkpoint 与业务状态冲突 | 图状态和 ERP/Frappe 事务不是同一事实源 | checkpoint 只保存执行进度，执行前重检业务事实 |
| 工具越权 | Prompt、RAG、Skill 或子 Agent 扩展能力 | 服务端 capability allowlist，模型不能自扩权 |
| 多 Agent 放大错误 | Reviewer 与 Planner 使用同类模型和上下文 | 独立证据、不同权限、确定性复核、A/B |
| 记忆污染和串租户 | 恶意内容或 scope 错误进入长期层 | candidate/approved 分层、scope filter、过期和审计 |
| 自进化造成行为漂移 | 自动 Prompt/Skill 更新绕过评测 | 离线候选、版本化、shadow eval、人工晋级、回滚 |
| 学习实验污染主线 | Web/GUI/shell 等宽权限工具进入 ERP Agent | `labs/` 与主 Runtime 隔离，架构测试禁止依赖倒流 |
| 框架锁定 | 领域状态直接等同 LangGraph/smolagents 类型 | 领域 schema 独立，框架通过 adapter 使用 |
| 训练实验虚假提升 | 数据泄漏、Judge 偏差、样本过小 | train/eval 隔离、确定性指标、人工盲测、报告置信区间 |

### 13.2 学习风险

| 风险 | 表现 | 控制方式 |
|---|---|---|
| Coding Agent 再次全程接管 | 代码完成但用户讲不清 | Assignment 和用户讲解成为出口硬门禁 |
| 知识点堆砌 | 仓库有很多 Demo，但没有联系 | 所有实验必须映射同一采购问题和 Adoption Card |
| 只会框架 API | 会 `create_react_agent`，不会解释循环 | 先手写内核，再使用框架，再做源码对照 |
| 为简历强行采用技术 | 多 Agent/向量库/K8s 只有名词 | 允许“不采用”，但必须有实验和证据 |
| 阶段再次膨胀 | 一个 Phase 同时做十种能力 | 每阶段只设一个核心学习主题，超出内容进入下一阶段 |
| 面试话术脱离代码 | 背诵架构但没调过问题 | 每个回答必须关联代码、Trace、测试或事故复盘 |

## 14. 原方案中保留的正确内容

V2 不是否定上一版全部设计。以下内容继续保留，但分散到正确阶段：

- Direct、Bounded ReAct、Plan-and-Execute 混合路由；
- 模型负责开放式调查和规划，确定性代码负责权限、金额、审批、幂等和写入；
- typed tool registry、dynamic allowlist 和 proposal/write 分离；
- 多层停止条件和轨迹评测；
- 四层记忆与实时 ERP 事实强制回查；
- Planner/Reviewer/Reconciliation typed handoff；
- 真实 ERP read-back、Receipt 和 reconciliation；
- Prompt、Skill、Model、Tool schema 的版本和 provenance；
- 阶段 Rubric、风险登记和最终独立对抗审查。

变化不是把这些删除，而是把它们从一个畸形 Phase 4 拆回完整学习路线。

## 15. 已批准的方向决定

用户已于 2026-08-26 批准下列全部路线级决定：

1. 项目定位为“Agent 岗位学习仓库 + 真实 ERP 实践载体”，商业化最小范围不是最高优先级；
2. 在同一仓库和开发主线中采用“业务应用层 + Agent 教学实验层”，不拆仓库或长期分支；
3. 废止原 Phase 4–8 排期，按本文 Phase 4–13 重排；
4. Phase 4 只做执行内核、Tool Calling、停止治理和第一版 Eval，不加入写入、记忆和多 Agent；
5. Phase 5 通过手写实现和对照实验后，再决定 LangGraph 在主线中的最终范围；
6. Phase 6 的 MR/PO Draft 是第一个真实 Agent 行动闭环；
7. Web/GUI/多模态（Phase 11）与自进化/后训练/Agentic RL（Phase 12）是必做学习阶段，是否进入业务主线由证据决定；
8. 用户 Assignment、亲手运行、设计讲解和面试追问是阶段出口条件。

按已批准决定，下一步仍然不是立刻编码，而是：

1. 把批准后的定位和 Phase 4–13 路线同步到权威文档；
2. 为 Phase 4 写一份不超过当前阶段范围的实施设计；
3. 先给用户 Phase 4 第一个 Assignment：手写最小采购 ReAct loop；
4. 建立第一批工具调用 golden cases 和 Trace schema；
5. 用户完成或明确请求接手后，再进入业务主线实现。

本文已从提案转为批准的方向基线。批准只授权同步文档和准备后续阶段；Phase 4 仍需按 `docs/PLAN.md` 完成 Assignment、前置证据和启动门禁，不得因本批准被写成已实现。
